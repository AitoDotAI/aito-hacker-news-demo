# aito-hacker-news-demo

**Predict how a Hacker News submission will do — from its title, domain, and posting time — with the [aito.ai](https://aito.ai) predictive database.**

Live: [hacker-news.aito.ai](https://hacker-news.aito.ai)

Type a candidate title, pick a domain and a posting hour/day, and Aito predicts the likely score bucket (and front-page odds) by querying a corpus of past HN submissions — no trained model, just `_predict` / `_relate` / `_match` over an indexed table. Every prediction comes with the similar past posts and the title tokens / domains / hours that drove it.

## How accurate is it?

Barely, and we measured it rather than guessing. `scripts/evaluate.py` holds out submissions posted *after* the corpus ends — so the index has never seen them — and scores them through the demo's own predict path:

| | AUC | top-decile lift |
|---|---|---|
| **as shipped (all fields)** | **0.599** | 1.9x |
| title only | 0.514 | 1.3x |
| domain only | 0.607 | 2.4x |
| title length only | 0.481 | 1.3x |
| posting hour only | 0.531 | 0.9x |

0.5 is a coin flip. So the demo's headline feature — *type a title, get front-page odds* — is measurably not doing much: **title wording is noise (0.514), and the domain alone (0.607) outperforms the full model.** The raw probabilities also run optimistic above ~20%, so `src/calibration.py` maps them onto observed frequencies from the holdout before the UI shows them.

We consider that a more interesting result than a demo that pretends otherwise. HN outcomes depend heavily on who is awake, what else is on the front page, and early-comment velocity — none of which is knowable from a draft title.

Reproduce it:

```bash
uv run python -m scripts.evaluate                # 700 held-out submissions
uv run python -m scripts.evaluate --n 900 --json data/eval-report.json
```

`data/eval-report.json` holds the run the numbers above come from.

## How it works

- **Data** — public Hacker News submissions in an Aito table `hn_submissions` (title, domain, posting hour/day, score bucket). Fetched with `scripts/fetch_corpus.py`, loaded into Aito with `scripts/load_aito.py`. The raw `data/*.ndjson` corpus is regenerated by those scripts and is not committed.
- **Backend** (`src/app.py`, FastAPI):
  - `POST /api/predict-hn` — score-bucket distribution + front-page %, similar past posts, and the "why" features for a candidate title.
  - `GET /api/category-features` — top predictive features per outcome bucket (via Aito `_relate`).
  - `GET /health`, `GET /api/health`, `GET /api/schema` — the platform's liveness/readiness/schema conventions.
  - Middleware surfaces `X-Aito-Ms` / `X-Aito-Calls` / `X-Aito-Ops` so the UI's LatencyBadge can show live query timings.
- **Frontend** (`frontend/`, Next.js 16 static export) — the title-tester UI plus a feature-explorer page. In production a single uvicorn process serves both `/api/*` and the exported UI.

## Local development

```bash
./do install     # uv sync + npm install
./do dev         # uvicorn backend + next dev frontend (hot-reload; frontend proxies /api/*)
```

Backend defaults to port `8401` (`BACKEND_PORT`), frontend to `3000`. The dev-only `next.config.ts` rewrite proxies `/api/*` to the backend; production skips it.

## Loading the corpus

```bash
python scripts/fetch_corpus.py     # → data/submissions.ndjson (public HN data)
python scripts/load_aito.py        # upload into the hn_submissions table of the configured Aito instance
```

Point `AITO_API_URL` / `AITO_API_KEY` (see below) at your Aito instance first.

## Environment

Copy `.env.example` to `.env` and set:

```
AITO_API_URL=https://<your-aito-instance>
AITO_API_KEY=<read-only key>
```

The read key is intentionally read-only — it's safe in the browser-facing build. (When hosted by `aito-demo-server`, these are remapped from the platform's per-demo secrets `AITO_HACKER_NEWS_API_URL` / `AITO_HACKER_NEWS_API_KEY`.)

## MCP / Claude Desktop

The same prediction and feature-discovery primitives exposed at `/api/*` are also available as **MCP** tools, so Claude Desktop (or any MCP client) can test titles against the corpus directly.

| Tool                            | Returns                                                  |
|---------------------------------|---------------------------------------------------------|
| `predict_hn_title`              | front-page %, bucket distribution, similar posts, why    |
| `discover_category_features`    | top features per bucket (via `_relate`)                  |
| `find_similar_hn_posts`         | just the similar-posts list, no prediction overhead      |
| `predictive-hn://schema` (rsrc) | the live `hn_submissions` schema                         |

Run it standalone:

```bash
./do mcp           # stdio transport; ctrl-C to stop
```

Wire into Claude Desktop — add to `claude_desktop_config.json` (Linux: `~/.config/Claude/claude_desktop_config.json`) and restart:

```json
{
  "mcpServers": {
    "predictive-hn": {
      "command": "uv",
      "args": ["--directory", "/absolute/path/to/aito-hacker-news-demo", "run", "python", "-m", "src.mcp_server"]
    }
  }
}
```

Prerequisites the subprocess assumes: the `hn_submissions` table loaded (`scripts/load_aito.py`) and a `.env` with `AITO_API_URL` + `AITO_API_KEY`. Then ask things like *"would 'Show HN: Introducing Predictive Application' do well on Hacker News?"* and it'll call `predict_hn_title` and reason over the bucket distribution + similar past posts.

## Tests

```bash
./do test          # pytest + booktest snapshot tests (book/)
```

`book/` holds Aito-dependent snapshot tests (replayed from recorded responses on later runs); `tests/` holds pure-logic unit tests.
